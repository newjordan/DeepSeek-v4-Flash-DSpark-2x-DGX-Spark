## Measured — decode is ~3× below the recipe's audited expectation

Method = the recipe's own `scripts/EVAL.md` rules, re-implemented in bash
(`bench-gb10/decode_bench.sh`; python3 is blocked on this rig by `spark-gpu-admit-hook`
while DS4 holds unified memory): cold prefill via unique nonce, decode window excludes
TTFT (`(completion_tokens-1)/(t_last-t_first)`), token count from `usage.completion_tokens`
with `stream_options.include_usage`, server warmed first.

## Root-cause evidence: the GPU is software power-capped at ~30 W

Sampled during sustained 1000-token decode (`bench-gb10/sample_load.sh` + `nvidia-smi -q -d PERFORMANCE`):

| node | GPU util | SM MHz (max 3003) | power W | `SW Power Cap` |
|---|---|---|---|---|
| head | 95–96 % | 2470–2528 | 27.8–31.7 | **Active, every sample** |
| worker | 86–87 % | 2470 | 31.6–37.8 | **Active, every sample** |

- No HW thermal/power-brake slowdown active; governor `performance`; load average 1.84/20 cores.
- Cumulative `SW Power Capping` counter on head = **49,578 s** against ~14 h container uptime — capped essentially the whole time.
- For contrast, H3/ComfyUI renders on this *same* toymaker GPU sustain **85–92 W** at SM 2216–2411
  (see `~/h3/PERFORMANCE.md`). DS4 decode never leaves ~30 W.
- High SM utilization at low power = memory-stalled/clock-limited, not compute-saturated.

This is consistent with upstream **issue #79** (fixed 2026-08-18 in `689ba32`,
`patches/hotfix-gb10-spin-wait.sh`): the vLLM shm `SpinCondition.busy_loop_s=1` never falls
through to sleep for decode IPC, so Grace P-cores busy-spin and consume the shared GB10
power budget. **The container measured here predates that fix** (started 04:38 UTC; fix
committed 17:45 UTC), so this baseline is a clean "before".
Upstream published **no numbers** for #79.

## Open leads (unmeasured anywhere in the repo)

1. **#79 spin-wait fix** — no upstream numbers; direct candidate for the power cap above.
2. **`max_num_batched_tokens`** — the live server logs, twice per rank:
   `max_num_scheduled_tokens is set to 8168 based on the speculative decoding settings.
   This may lead to suboptimal performance. Consider increasing max_num_batched_tokens…`
   No A/B of 8192 vs 16384 exists in `results/`.
3. **`VLLM_B12X_W4A16_FORCE_BLOCKS_PER_SM` / `_BLOCKS_MAX_M` (currently 16) / `_TILE_CONFIG`** —
   three registered, experimental W4A16 MoE kernel-selector knobs with **zero measurements** in the repo.
   `W4A16FusedMoeKernel` was observed JIT-compiling *during inference* (08-18 05:19), i.e. warmup
   does not cover the served shapes.
4. **Acceptance deficit** — 43 % vs 68–75 % published. Costs decode directly (mean accept 3.16 vs ~4).
5. **MTU 1500** on the RoCE link (no jumbo frames).
6. `GPU_MEMORY_UTILIZATION_TEXT` 0.80 vs recipe 0.835 — the one deliberate local delta.
