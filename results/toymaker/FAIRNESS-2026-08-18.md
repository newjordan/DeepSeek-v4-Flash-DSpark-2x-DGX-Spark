```
lane      in  TTFT(s) whole_t/s  postTTFT_t/s p95ITL(ms)   out

   3   63488  117.995      1.88         14.27     6013.1    46
   4   63488  264.571      0.91         14.57     5812.6    46
   5   63488  154.647      1.49         15.37     6149.0    44
   6   63488  293.861      0.87        134.56      717.8    44   <-- last to prefill
   7   63488  191.253      1.22         14.31     5828.7    46
  wave wall = 295.773 s
```

TTFT is staggered almost linearly (44.8 → 293.9 s) because the eight cold 62K prefills are
serialized through the chunked-prefill budget. Every lane that has *already* started decoding
is then interleaved against the remaining prefill work, so it decodes at ~14–15 tok/s with a
**p95 inter-token latency of ~6 seconds**. The single exception is lane 6: it is the last to
finish prefilling, so by the time it decodes the prefill backlog is empty and it runs at
**134.6 tok/s with 718 ms p95** — roughly 9× the others.

So the honest statement of the weakness is not "unfair throughput" but:

> **While a long-prefill backlog is draining, every already-admitted lane sees multi-second
> gaps between tokens.** At 62K×8 that lasts the ~5-minute length of the wave.

For an interactive agent this reads as the model hanging. For a batch chain it is merely slow.

## Operational guidance

1. **Stagger admission of long chains.** The damage is caused by concurrent *cold prefills*,
   not by concurrent decoding. Eight 62K chains admitted together cost every one of them a
   ~6 s p95 ITL for five minutes; the same eight admitted serially do not.
2. **Warm chains are cheap — reuse prefixes.** Prefix-cache retention is healthy here
   (8/8 lanes, hit ratio 0.9735, see `QUALITY-STABILITY-2026-08-18.md`), and a warm replay of a
   131k context cost 3.9 s against 71.4 s cold. Multi-turn chains that grow one prefix are
   dramatically better behaved than many independent long contexts.
3. **The documented lever is blocked on this image.** `MAX_NUM_PARTIAL_PREFILLS=2/3` is what
   the recipe names as "the lever that improves the whole-request min/max decode rate #43
   reports", but `.env.dspark.example:126-134` records that vLLM's `_check_feature_supported()`
   rejects Concurrent Partial Prefill on `dspark-vllm-gx10:0.1.1` before engine init — even an
   explicit `--max-num-partial-prefills 1` trips the guard. It needs a base-image upgrade.
4. `MAX_NUM_BATCHED_TOKENS` 8192 → 16384 is still unmeasured and is the plausible remaining
   knob here (it would drain the prefill backlog faster at some cost to decode interleaving).
   The server already warns `max_num_scheduled_tokens is set to 8168 … may lead to suboptimal
   performance`.

## Do not quote the acceptance numbers from this run

The cells report `[mtp] rate=96.9–97.6%`, far above the 43–48 % measured on real content
(`SERVING-POSTURE-2026-08-18.md`). This harness pads with repetitive filler, and
`scripts/EVAL.md` documents that repeated-token prompts distort the drafter. These figures
measure the filler, not the workload.
